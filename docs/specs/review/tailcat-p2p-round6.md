## 新 findings

### S1（作为 Phase 1 设计依据或提交批准 (B) 之前必须修订）

#### S1-1 入站静默（I3）与 DirectGateOpen / 入站缓存（I24）一起读时，闸门语义没有闭合

- **位置**：
  - `docs/specs/tailcat-p2p.md:67`（第 6 步）、`:77`、`:79-82`（§2）、I3 `:261`、I24 `:282`；
  - 用例 `:310`、`:443`、`:450-452`；
  - feature map F4、F5，以及时序图 `:58-60`。
- **问题**：
  1. **静默计时从什么时候开始没写，按字面会死锁。**
     - I3 要求被控端闸门"连续 1000 ms 无入站即关"。
     - I24 要求被控端闸门打开后才发 `DirectGateOpen`，控制端收到之后才发首个 QUIC 包。
     - 所以闸门打开的那一刻，这个流上必然还没有入站数据报。如果静默按"最后一次入站距今 > 1000 ms，或从未有入站"判定，闸门要么打不开，要么一开就关。
     - 即使从开闸时刻起计时，首包到达要经过：中转单程 + 控制端等本端闸门（Phase 0 范围 −163 至 +114 ms）+ 直连单程。Phase 0 的数据是：中转端到端单程最高 400 ms，直连单程最高 200 ms。离 1000 ms 没有写明的余量；中转 RTT 再高一些就会误关。
  2. **静默关闭之后会怎样没写**：本 `epoch` 内是否粘性关闭（转回退、换新 `epoch`）？重新打开的条件是什么？要不要再发一次 `DirectGateOpen`？
  3. **闸门管哪个方向，前后矛盾。**
     - §2 `:77` 只定义了出站方向："丢弃来自 Rust 一侧的数据报"。
     - I24 的根因，以及"入站缓存"这个等效实现，都以被控端闸门**丢弃入站**的控制端 Initial 为前提。
  4. **入站缓存作为等效实现，与 I24 的条文和用例都冲突。**
     - I24 第一句是"控制端在被控端闸门打开之前，不得发出首个直连 QUIC 包"；缓存方案恰恰就是控制端在闸门打开前发包。
     - `controller_waits_for_direct_gate_open_before_first_quic` 与 `host_sends_direct_gate_open_when_gate_opens` 在缓存方案下没有对象。规格却说等效方案"须通过同一用例"，`:450` 又写"或等效缓存未生效"，口径不一。两种方案真正共有的只有 `upgrade_not_bimodal_from_dropped_initial`。
- **依据**：
  - Phase 0 报告 §3 第 3 项：spike 的静默条件是"flow 上 1000 ms 无入站数据报"，判定时间差 93–111 ms；
  - Phase 0 报告 §3 第 9 项：中转晚到时间表；
  - spike 的 flow 生命周期不进入 Phase 1，规格必须自己定义。
- **建议**：
  1. 写明静默计时只在本 `epoch` 的流上**出现首个入站数据报之后**才生效；或者开闸后先给一段宽限期（≥ `upgrade_timeout_secs` 的剩余部分），宽限期内只靠 `CurAddr` 和升级超时约束。
  2. 写明静默关闭在本 `epoch` 内是粘性的：直接转回退，不重开，不再发 `DirectGateOpen`。
  3. §2 明确闸门是双向的：入站方向在开闸前丢弃（或缓存），出站方向在开闸前丢弃。
  4. I24 改为按方案分写：
     - (a) DirectGateOpen 方案，沿用现有两个用例；
     - (b) 缓存方案：不变量写成"控制端首个直连 QUIC 包不得因被控端闸门关闭而丢失"，并给出它自己的用例；
     - 两种方案都必须通过 `upgrade_not_bimodal_from_dropped_initial`（建议改成确定性断言，见 S3-1）。
  5. 补用例：
     - `host_gate_rx_silence_not_armed_before_first_inbound`（或宽限期版本）；
     - `rx_silence_close_is_sticky_within_epoch`。

#### S1-2 批准 (B) 前的真机复核没有可判定的通过条件

- **位置**：`:336`、`:373-381`、`:361`、`:364`、`:309`、`:514`；open question 16。
- **问题**：
  1. **k 没有定为判据。** `:380` 写"若真机 5 分钟 R 按 C ≤ k×R（k < 1）无法支撑 C = 100 Mbps"。只要 k 能任意接近 1，任何 R > 100 Mbps 都算"支撑"，这个门禁就失去了意义。
     - r6 的推导靠的是 k ≈ 0.5，加上一个只跑了 30 s 的 200 Mbps 短测。
     - 按 `:373` 自己的定义，R 是"持续吞吐"，而 5 分钟只证实了 60 Mbps。所以以现有数据看，C = 100 Mbps 并不满足 C ≤ k×R，只是暂定值。规格对这一点的表述是诚实的，但复核时按什么标准判定，没有写。
  2. **C 码率下的 CPU 没有阈值，也没有数据。** 现有 CPU 阈值定义在约 20 Mbps 下。Phase 0 清单第 11 项要求测 C 码率下的 CPU，但 100 Mbps 下没有测；200 Mbps 下被控端为 40–51%。规格没有写明这一项尚未完成，也没写真机上 100 Mbps 的 CPU 怎样算可接受。
  3. **托管 DERP 的复核没有期望值**：结果必须是 0 包，还是允许一个有界值？不是 0 时怎么办？
  4. **真机测什么没写。**
     - Phase 1 代码要等批准 (B) 之后才写，所以 (B) 之前能上真机的只有 spike（PR #3）。
     - spike 没有实现 I24 和 I25（Phase 0 报告：两档耗时是实测现象，写超时只是建议）。
     - 规格没写真机复核用哪份代码、spike 能否在批准 (A) 的范围内补这些修正，也没写 I24 / I25 是否只在 Phase 1 验收时才验证。
  5. **复核托管 DERP 要联系第三方服务。** Phase 0 报告 §5 写的是"获准后使用"，规格没写这项测试本身也需要项目负责人许可。
- **依据**：
  - 阶段表 `:336` 把"C 与 I3 窗口（含托管 DERP）须用真机数据复核"列为批准 (B) 的前提；
  - workflow-v2 规定 spec 与评审都不代替批准，门禁必须可以判定。
- **建议**：增加一张"批准 (B) 前真机复核判据"表。只写判据，不安排机器和时间。
  - 码率：固定 k = 0.5，即要求在参考硬件上、选定通道上 R ≥ 200 Mbps × 5 min，丢包 < 0.1%。不达标就提交项目负责人另定 C；不在规格内自动降档。
  - CPU：给出 C 码率下的 helper CPU 判据，或者明确交给 (B) 时由项目负责人判断。
  - 托管 DERP：期望 0 包；不是 0 时提交项目负责人决定。
  - 被测对象：写明用 spike 分支做复核（是否允许在 spike 上补 I24 / I25 / 静默修正，属于批准 (A) 范围内的问题，须项目负责人确认）；I24 / I25 归入 Phase 1 验收。
  - 写明托管 DERP 复核须项目负责人许可。
