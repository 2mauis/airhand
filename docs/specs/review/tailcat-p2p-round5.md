# 第 5 轮复审：tailcat 直连规格 r5

## 结论

**有条件通过。本轮没有 S1。**

- **主线自洽。** "取得同意之前不交换地址、不启动 helper、不联系 DERP"这条不变量，在 never 模式允许直连之后仍然成立。I12、I16、I21 对"同意"的定义一致，下列各处都按同一口径改写，没有发现漏改：
  - 握手第 2 步、第 5 步（`docs/specs/tailcat-p2p.md:63`、`:184`）；
  - 配置表（`:212`）、安全模型（`:141-145`）、非目标（`:236`）、风险（`:401-402`）；
  - 验收用例（`:275`、`:282`）和 feature map 的 F21、F22。
- **两种"只开一项"的情况都写清了。**
  - 只开 `never`：`granted.direct` 为假，不交换地址，不启动 helper（I21）。
  - 只开 `[direct] enabled`（`ask` 模式）：必须在确认窗里勾选"允许直连"（`:143`、`:180`）。
- **没有重新引入"未同意就交换地址"的路径。** never 路径上，被控端仍然要等 `HostHello` 发出、并收到 `DirectRequest` 之后才启动 helper；控制端要等收到 `granted.direct = true` 之后才创建 helper。
- **不能自洽的是 never 路径上的"排除项"。** r4 为 `ask` 写的几条保证，正文仍写成无条件成立，但在 never 路径上已经不成立，规格既没有排除，也没有替代方案（见 S2-1、S2-2）：
  - 授权记忆里"直连权限每次重新确认"；
  - 被断开的设备"不能免确认回来"；
  - 指示条收回权限；
  - 锁屏下的常驻指示。
- **"运营者配置即同意"缺少边界。** 已获输入权限的远端，可以通过注入输入去改配置，把自己变成"运营者"（S2-3）。
- 第 2、3、4 项决定与正文、I18、配置默认值、SAS 用例一致。码率上限策略已经关闭第 3 轮 S2-3 的"限制码率还是回退"部分。

### S2（批准 (B) 之前必须关闭）

#### S2-1 never 路径上，授权记忆、"断开此控制端"、收回直连这三条保证反了过来，正文仍写成无条件成立

- **位置**：`:183`（"直连权限不随记忆复用，每次新会话都要重新确认"）、`:192`（"被断开的设备……不能免确认回来"）、`:185` 与 I20（收回直连）、§2 `:93`（回退后每 30 秒重试，最多 3 次）、用例 `kicked_device_must_reapprove`、`direct_grant_not_reused_on_reconnect`
- **问题**：never 模式下，每个新会话都按 I21 自动授予直连，因此：
  1. 被"断开此控制端"的设备手动重连，立即免确认回来，并且重新获得直连；
  2. 指示条收回直连只在当前会话有效，对方断开重连就恢复了；
  3. 收回直连之后，规格没写本会话是否还会按 `:93` 的规则自动重试升级。
- **依据**：I21（`granted.direct` 只取决于配置）。I23 写的是 never 模式"跳过询问"，但 `:183`、`:192` 没有写例外。
- **建议**：
  - 在 `:183`、`:192`、I18、I20 里明确写"仅 ask 模式"。
  - 写明 never 模式下，能阻止持码人回来的手段只有：停止共享（换码）、关闭 `never`、关闭 `[direct] enabled`。可以考虑让 never 模式的 Kick 把该设备加入本次运行的拒绝表，这属于会话策略，须项目负责人确认。
  - 写明收回直连在本会话内是粘性的：不再按 `:93` 重试。
  - 补用例：`never_mode_kicked_device_can_return_only_until_code_changed`（或者拒绝表方案对应的用例）、`revoked_direct_not_retried_in_session`。

#### S2-2 Windows 登录屏 / 锁屏下，never + 直连没有本机指示条，与 I22、I10 和"主动断开"一节矛盾

- **位置**：`:206`（"此时没有本机指示条，直到有可显示托盘的会话"）对比 I22（`:262`）、I10、`:190`（"会话期间显示常驻的……指示"）、`:186`（SAS 显示在指示条上）
- **问题**：
  - 这是 never 路径上最典型的无人值守场景。在这个场景里，I22 的常驻指示、本机收回权限、一键停止共享、SAS 显示都不存在，I22 却没有写例外。
  - 这条路径还依赖 Windows SYSTEM agent 拉起受限令牌 helper。如果 Phase 0 证实不可行，按退路（`:147`），Windows 安装版作为被控端时整体禁用直连，never + 直连在 Windows 安装版上也就不可用。
- **建议**：二选一，并写进 I22 和风险。
  - (a) 明确把这种情况排除出 I22，并说明锁屏期间能用的远程停止手段（只有控制端断开，或者运营者通过其他途径换码）；
  - (b) 无法显示指示条时不升级直连。这改变了会话策略默认值，须项目负责人确认。

  另外，在 r6 里写明 Windows 结论对 never + 直连的影响。

#### S2-3 "运营者显式配置即同意"没有界定配置的来源：已获输入权限的远端可以改配置，把自己变成"运营者"

- **位置**：`:142-145`（"持码人本人不能单方面触发"；"首次启用与开启 never 时提示"）、I21、"防注入"（`:200-202`）
- **依据**：
  - macOS / Linux 的 `config.toml` 在用户目录里（`client/src-tauri/src/config.rs:133-135`）。
  - Windows 的配置文件在安装目录，托盘没有写权限（`config.rs:132`、`winsvc/ipc.rs:74`）。
  - 运行中会跟踪配置文件内容（`config.rs:503-547`）。
- **问题**：
  1. 在 ask 模式下获准"输入控制"（默认开）、但没有获准直连的控制端，可以用注入的键鼠编辑配置，设成 `approve = "never"` 并打开 `[direct] enabled`。之后它再连接时就免确认，并且自动获得直连。这正好是 `:142` 禁止的"持码人单方面触发"，r4 的防注入措施也没有覆盖这条路径。
  2. 规格没写 `approve`、`[direct]` 什么时候读入：启动时读一次，还是每个会话读一次。
  3. "首次启用与开启 never 时提示"由谁弹、什么时候弹、能不能被注入输入点掉，都没定义。
  4. 还要如实说明：已获输入权限的控制端，本来就能借浏览器、系统命令得知本机 IP。所以"直连同意"主要防的是没有输入权限的控制端，以及未来未经同意的会话，而不是已获输入权限的当前会话。这一点应写进 `docs/security.md` 的表述里。
- **建议**：
  - 写明这两个键的读取时机。
  - 有已授权且带输入权限的会话在途时，对 `approve` / `[direct]` 的改动不生效（或者推迟到所有会话结束、重启之后，并由本机确认）。确认提示受"防注入"约束。
  - Windows 上写明只有管理员能改。
  - 补用例：`config_change_to_never_during_input_session_not_applied`、`enable_never_prompt_rejects_injected_input`（手动）。
